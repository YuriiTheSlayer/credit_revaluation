# Payment Terms Dashboard — Анализ сроков рассрочки Comfy vs конкуренты

Локальное десктоп-приложение (один `.exe`, запуск без установки и без интернета) для анализа
количества платежей рассрочки по товарам Comfy в сравнении с конкурентами, с разрезом по
банкам-партнёрам и экспортом готового отчёта в Excel.

---

## 1. Назначение

Приложение принимает на вход:

1. **CSV-выгрузку по конкурентам** (пример: `Книга31.csv`) — условия рассрочки по каждой SKU
   в разрезе *банк × конкурент*;
2. **Файл продаж** (загружается отдельно) — суммы продаж по SKU за период.

И строит интерактивный дашборд, аналогичный эталонному отчёту `claude_example.xlsx`,
с возможностью выгрузки результата в `.xlsx` в том же формате.

Ключевая метрика — **средневзвешенный срок рассрочки (кол-во платежей)** по Comfy и по
каждому конкуренту, рассчитанный **внутри категории** как сумма произведений
(SUMPRODUCT) доли товара на его количество платежей.

## 2. Входные данные

### 2.1. CSV по конкурентам (`Книга31.csv` — пример)

| Параметр | Значение |
|---|---|
| Кодировка | **Windows-1251 (cp1251)** — обязательна перекодировка при чтении |
| Разделитель | `,` (запятая) |
| Конец строки | CRLF |
| Заголовок | 1-я строка; 2-я строка — служебная/мусорная (`,,,,...,25;`) — пропускать |

**Колонки:**

`КодТовара, Товар, Бренд, Подкатегория, Категория, Бизнес, Атрибут_RMA, Товар поставщика, Остаток_Comfy, Остаток_SP, Скидка, Цена Comfy *, Маржа кредитная, Конкуренты. MAX платежей, Comfy. MAX платежей, Откл. MAX платежей, Шаг, Тип ассортимента, ТипАссортиментаОбщий, Банк, Конкурент, max(КолвоПлатежей)`

**Особенности формата (требуется устойчивый парсер):**

- Строка имеет «двойную» структуру: `КодТовара,Товар;"КодТовара,Бренд,...,N"` — вторая часть
  строки обёрнута в кавычки и содержит повтор кода товара. Поле `Товар` фактически равно
  `Название;КодТовара`. Парсер должен:
  - читать строку штатным CSV-ридером (кавычки RFC-4180);
  - «разворачивать» вложенный quoted-блок во вторую часть колонок;
  - нормализовать поле `Товар` (отрезать `;КодТовара`).
- Числа в «европейском» формате: пробел как разделитель тысяч (`6 649`), запятая как
  десятичный разделитель (`14,3%`, `10,91`). Значение `-` в колонке `Шаг` → `NULL`.
- Денормализация: **одна SKU повторяется на каждую комбинацию Банк × Конкурент.**
  - Банки в примере: `Monobank`, `ПриватБанк`, `ПУМБ` (список не хардкодить — брать
    distinct из файла).
  - Конкуренты в примере: `foxtrot.com.ua`, `rozetka.com.ua` (аналогично — distinct из
    файла; в эталонном отчёте встречается также Epicentr).
- `max(КолвоПлатежей)` — кол-во платежей у данного конкурента в данном банке.
- `Comfy. MAX платежей` — кол-во платежей у Comfy (своя витрина) для сравнения.

### 2.2. Файл продаж (отдельная загрузка)

Простой плоский файл из двух колонок:

| Колонка | Описание |
|---|---|
| `КодТовара` (SKU) | ключ связи с CSV конкурентов |
| `Оборот` | сумма продаж за период, грн |

- Форматы: `.csv` (cp1251/UTF-8 — автоопределение) и `.xlsx` (первый лист).
- Названия колонок не критичны (`SKU`/`КодТовара`, `Оборот`/`Продажи`) — определяются по
  содержимому: колонка с кодами + числовая колонка.
- Дубликаты `КодТовара` — обороты суммируются.
- Связь с CSV конкурентов — left join по `КодТовара`: SKU без оборота получают 0 и не
  участвуют в весах листа «на продажи»; SKU из файла продаж, отсутствующие в CSV
  конкурентов, игнорируются (предупреждение в лог со списком).
- В отчёте колонка `Продажи` = `Оборот` из этого файла.

## 3. Логика расчёта

### 3.1. Переключатель банка (обязательное требование)

В CSV присутствуют **несколько банков**. В интерфейсе — переключатель (сегмент-контрол или
дропдаун): `Monobank | ПриватБанк | ПУМБ | ...` (+ опционально режим «Все банки» с
агрегацией `max` по платежам). Все таблицы, метрики и экспорт пересчитываются под выбранный
банк. После выбора банка данные пивотируются:

```
строка = SKU, колонки = Кол-во платежей {Comfy, Foxtrot, Rozetka, Epicentr, ...}
```

### 3.2. Структура (вес товара внутри категории)

Расчёт ведётся **внутри каждой категории** отдельно:

- **Лист «Ср. срок на продажи»** — вес по продажам:
  `Структура_i = Продажи_i / Σ Продажи (по категории)`
- **Лист «Средний срок на стоимость»** — вес по цене:
  `Структура_i = Цена_i / Σ Цена (по категории)`

При активных фильтрах (бизнес, категория, тип ассортимента и т.д.) знаменатель берётся
по отфильтрованному набору SKU — веса перенормируются, чтобы их сумма внутри категории
была равна 1.

### 3.3. Средневзвешенный срок (сумма произведений)

Для каждого ритейлера R (Comfy и каждый конкурент) внутри категории:

```
СрСрок(R) = Σ_i ( Структура_i × КолвоПлатежей_i(R) )   // SUMPRODUCT
```

Это итоговая строка отчёта (в эталоне: Comfy 16.41, Foxtrot 14.49, Rozetka 15.46,
Epicentr 14.60 для категории «Смартфон»). SKU с пустым значением платежей у конкретного
ритейлера исключаются из расчёта этого ритейлера с **перенормировкой весов** (чтобы сумма
весов участвующих SKU была равна 1) — иначе средняя занижается.

### 3.4. Производные показатели

- `Откл. MAX платежей = Comfy − max(конкуренты)` по SKU;
- подсветка SKU, где Comfy проигрывает конкурентам (откл. < 0);
- доля SKU, где Comfy ≥ лучшего конкурента, по категории.

## 4. Дашборд (UI)

Один экран, локально в окне приложения:

1. **Панель загрузки** — две зоны drag-and-drop: «CSV конкурентов» и «Файл продаж»;
   валидация структуры с понятными сообщениями об ошибках (кодировка, отсутствующие
   колонки, нет пересечения по КодТовара).
2. **Переключатель банка** — закреплён сверху, влияет на всё.
3. **Фильтры (обязательное требование)** — блок фильтрации по классификатору и ассортименту:
   - **Бизнес** (верхний уровень классификатора);
   - **Категория** и **Подкатегория**;
   - **Тип ассортимента** и **ТипАссортиментаОбщий** — два независимых фильтра, в данных
     это разные поля (Матрица/Нематрица/Поставщик/ВП и Роздрібна матриця/Додатковий/...);
   - дополнительно: Бренд, поиск по названию/коду товара.

   Все фильтры — мультивыбор со значениями distinct из загруженного файла; влияют на
   KPI-карточки, таблицу, графики и экспорт. При активных фильтрах веса (Структура)
   пересчитываются по отфильтрованному набору SKU внутри категории — иначе SUMPRODUCT
   перестаёт быть корректным средневзвешенным.
4. **KPI-карточки** — средневзвешенный срок Comfy vs каждый конкурент (для выбранного
   банка и фильтров), дельта в платежах.
5. **Таблица SKU** — колонки как в эталонном xlsx; сортировка; условное форматирование
   колонки «Откл. MAX платежей» (красное — проигрываем, зелёное — выигрываем).
6. **Графики** — bar chart «средний срок по ритейлерам» по категориям; распределение
   отклонений.
7. **Кнопка «Экспорт в Excel»**.

## 5. Экспорт в Excel

Файл повторяет структуру `claude_example.xlsx`:

- Лист **«Ср. срок на продажи»** — SKU-таблица + колонка `Продажи` + `Структура`
  (доля в категории по продажам) + итоговая строка SUMPRODUCT по каждому ритейлеру
  с подписями ритейлеров под итогами;
- Лист **«Средний срок на стоимость»** — то же, но веса по цене;
- В имени файла и в шапке — выбранный банк и дата формирования
  (`report_Monobank_2026-06-10.xlsx`);
- Форматирование: проценты для маржи, разделители тысяч для цен/продаж, заморозка шапки,
  автофильтр, условное форматирование отклонений.

Экспортируются данные **с учётом текущих фильтров и выбранного банка**. Опция «экспорт по
всем банкам» — один файл, по паре листов на банк (или банк в отдельной колонке — решить на
этапе UI-ревью).

## 7. Граничные случаи и валидация

- **Кодировка**: автоопределение cp1251/UTF-8 (BOM, chardet); понятная ошибка, если файл бинарный.
- **Служебная вторая строка** CSV — пропуск по эвристике (пустые ключевые поля).
- **SKU без продаж** — нулевой вес на листе «на продажи», но участвует в листе «на стоимость».
- **SKU без данных по конкуренту** — исключение из SUMPRODUCT этого конкурента с перенормировкой весов.
- **Дубликаты** SKU×Банк×Конкурент — берём `max(КолвоПлатежей)`, пишем предупреждение в лог.
- **Новый банк/конкурент** в файле — подхватывается автоматически (никаких хардкодов).
- `Шаг = "-"` и прочие плейсхолдеры → `NULL`.
- Большие файлы (100k+ строк) — чтение чанками, UI не блокируется (расчёт в отдельном потоке).

### 10.4. Принятые решения и отличия от эталона

1. **`Товар` нормализован** (хвост `;КодТовара` отрезан — §2.1); в эталоне
   хвост остался от ручной сборки.
2. **«Откл. MAX платежей»** в таблице и экспорте пересчитывается по выбранному
   банку (`Comfy − max(конкуренты банка)`, §3.4); в исходном CSV это поле —
   глобальный максимум по всем банкам, значения совпадают в режиме «Все банки».
   Исходное значение «Comfy. MAX платежей» из файла сохраняется в экспорте
   колонкой «Comfy MAX (файл)».
3. **Без файла продаж** колонки и итоги «по продажам» не формируются (веса
   не определены) — остаются веса по цене; после загрузки продаж всё
   пересчитывается.
4. **Загрузка файлов** — кнопки с системным диалогом **и** drag&drop прямо в
   окно (pywebview даёт полный путь файла); перетащенный файл распознаётся
   автоматически: csv конкурентов / файл продаж.
5. **Графики** — лёгкие SVG-диаграммы собственной отрисовки вместо Plotly:
   ноль внешних JS-зависимостей, полностью офлайн, tooltip'ы сохранены.
6. **KPI по нескольким категориям** считаются по весам, нормированным на весь
   отфильтрованный набор; в сводке экспорта — строго внутри категории.
7. **Python 3.11+** (разработка и тесты — на 3.11; рекомендованный §6
   Python 3.12 совместим).

### 10.5. Структура экспорта (переработана по итогам ревью)

Изначальный экспорт повторял эталон один-в-один (категорийные блоки с
промежуточными итогами на одном листе), но в работе это оказалось неудобно:
встроенный фильтр Excel по категории «резал» итоговые строки, а подписи
растекались по пустым ячейкам. Текущий формат:

* **«Сводка»** — итоги по категориям (сортировка по убыванию продаж):
  кол-во SKU, продажи, средневзвешенный срок каждого ритейлера в двух
  вариантах весов (продажи / стоимость; SUMPRODUCT с перенормировкой §3.3),
  доля SKU, где Comfy ≥ конкурентов. Первая строка — «Вся выборка». Ячейки
  конкурентов с бо́льшим сроком, чем у Comfy, подсвечены красным.
* **«Данные»** — все SKU одной плоской таблицей без промежуточных итогов:
  автофильтр по всему диапазону (фильтрация по категории работает корректно),
  зебра-подсветка строк, заморозка шапки и колонок Код+Товар, обе колонки
  «Структура», условное форматирование «Откл.». Значения записаны числами
  (не формулами) — файл лёгкий и быстрый даже на 90k строк.
* В первой строке каждого листа — банк, дата, активные фильтры и отметка
  о маппинге Comfy. Мультибанковый экспорт — пара листов на банк
  («Сводка — Monobank», «Данные — Monobank», …).

### 10.6. Маппинг доступности Comfy (Monobank)

Поле «Comfy. MAX платежей» в выгрузке — **максимальная** доступность Comfy,
т.е. условия уровня ПриватБанк/ПУМБ. В Monobank доступность Comfy снижена,
поэтому сравнивать конкурентов в разрезе Monobank с максимумом некорректно.

Кнопка **«Маппинг Comfy»** в дашборде открывает таблицу соответствия
«макс. доступность → доступность в банке» для всех значений, найденных в
файле (по умолчанию 1:1). Банк выбирается в диалоге (автоопределение по
подстроке «mono»). Когда выбран этот банк, приведённые платежи Comfy
используются во **всех** расчётах: KPI, таблице, отклонениях, сводке и
экспорте; «Все банки» и остальные банки продолжают использовать максимум.
Настройки хранятся в `~/.payment_terms_dashboard/comfy_mapping.json` и
переживают перезапуск приложения.

### 10.6.1. Доступность Apple (переопределение по бренду)

На технику Apple действуют особые условия рассрочки, и «Comfy. MAX платежей»
из выгрузки для неё неверно. Кнопка **«Доступность Apple»** открывает диалог,
где для каждого банка из файла указывается фактическое кол-во платежей Comfy
по товарам бренда (бренд настраивается, по умолчанию Apple):

* заданное значение **перезаписывает** значение из CSV во всех расчётах и
  экспорте (колонка «Comfy MAX (файл)» сохраняет исходное для аудита);
* пустое поле — банк продолжает использовать значение из CSV;
* переопределение **приоритетнее маппинга Comfy** (§10.6);
* в режиме «Все банки» берётся максимум: переопределённые банки против CSV
  для остальных;
* настройки хранятся в `~/.payment_terms_dashboard/brand_override.json`,
  активность видна бейджем в тулбаре и пометкой в шапке экспорта.

### 10.6.2. Сравнение по общему набору SKU

Галка **«Только SKU у всех конкурентов»** (в строке фильтров) исключает из
расчёта товары, по которым в выбранном банке нет данных хотя бы у одного из
конкурентов файла: средние сроки сравниваются по общему набору товаров.
Работает как обычный фильтр — влияет на KPI, таблицу, графики и экспорт
(отмечается в описании фильтров в шапке отчёта).

### 10.6.3. Предлагаемый кредитный маяк (КМ)

Колонка «Предл. КМ» в таблице дашборда; в экспорте — три колонки:
«КМ Comfy (ТОП банки)», «КМ рынка (ТОП банки)», «Предлагаемый КМ»
(реализация: `src/core/beacon.py`).

* **ТОП банки** — банки максимальной доступности (Приват/ПУМБ); технически
  все банки файла, кроме банка со сниженной доступностью (эвристика «mono»).
* **КМ Comfy** = среднее платежей Comfy по ТОП банкам (отличается от
  «Comfy. MAX платежей» только при переопределении бренда §10.6.1 с разными
  значениями по ТОП банкам).
* **КМ рынка** в разрезе ТОП банков:
  - `ТипАссортиментаОбщий = Spush` → **максимум** у одного из конкурентов;
  - прочие товары → **среднее по конкурентам** (значение конкурента —
    среднее его платежей по ТОП банкам).
* **Предлагаемый КМ** = КМ рынка, поднятый по «Матрице соответствия КМ» до
  ближайшей ступени лестницы сроков **3 / 5 / 7 / 10 / 12 / 15 / 18 / 20 /
  22 / 25** (рынок 4 → 5, 8 → 10, 13 → 15, 17 → 18, 19 → 20, 23 → 25;
  выше 25 → 25). Матрица закреплена тестом `tests/test_beacon.py` значение
  в значение.

### 10.7. Производительность (ориентир — CSV на 90k строк)

Замеры на синтетике 90 000 строк (15 000 SKU × 3 банка × 2 конкурента),
закреплены тестами `tests/test_perf.py`:

| Операция | Время |
|---|---|
| Парсинг CSV (cp1251, развёртка вложенных блоков) | ~3 с |
| Пивот банк→ритейлеры (15k SKU) | ~0.3 с |
| Метрики (структура + SUMPRODUCT по 80 категориям) | ~0.05 с |
| Экспорт листа «Данные» на 15k SKU | ~3 с |

Как достигается: пакетный разбор вложенных CSV-блоков одним `csv.reader`,
векторные преобразования чисел/строк (без поэлементных вызовов Python),
запись xlsx в режиме `constant_memory` числами без формул, кэш широких
таблиц по банкам в UI (повторное переключение банка мгновенно), парсинг и
экспорт — в фоновом потоке, таблица — с пагинацией (фронтенду уходит только
текущая страница и агрегаты, а не 90k строк).

### 10.9. JS-фронтенд (pywebview)

Интерфейс переведён с Flet на второй вариант стека из §6 — **pywebview +
HTML/CSS/JS**: нативное окно с системным WebView (Edge WebView2 на Windows)
и локальный фронтенд `src/webui/assets/` без единой внешней JS-библиотеки
(графики — рукописный SVG), полностью офлайн.

* **Архитектура.** Вся логика состояния — в Python (`src/webui/api.py`):
  фронтенд вызывает `window.pywebview.api.*` и получает готовый к рендеру
  JSON-снапшот. JS (`app.js`) — только отрисовка. Поэтому поведение UI
  покрыто обычными pytest-тестами без открытия окна
  (`tests/test_webui_api.py`).
* **Стилистика.** Корпоративные токены Comfy из `core/brand.py`
  прокидываются в CSS-переменные при старте — палитра приложения и
  Excel-отчётов управляется одним файлом.
* **UX.** Drag&drop файлов в окно (тип файла распознаётся автоматически),
  липкая шапка таблицы, сортировка кликом, мультиселекты с поиском,
  модальные настройки маппинга/Apple, тосты и индикатор занятости; тяжёлые
  вызовы (парсинг, экспорт) идут в фоновых потоках pywebview и не блокируют
  окно.
* **Сборка легче**: без Flutter-клиента exe заметно меньше (~40–60 МБ).
  Требование к среде — WebView2 Runtime (см. §10.3).

### 10.8. Корпоративный стиль (Comfy)

Палитра и мотивы перенесены из корпоративного фронтенда
**promo-self-service** (`theme.js`/`styles.css` — адаптация брендбука):

* зелёный `#2ABD13` — primary-действия и серия Comfy на графиках,
  тёмно-зелёный `#1F8E0E` — ховеры/«выигрываем», подложка `#E8F6E5`;
* оранжевый `#FC5E0F` — акцент/CTA и фирменная **«оранжевая точка»**
  (логотип, заголовки секций и модалок);
* графит `#2D2D2D` — текст, `#4A4A4A`/`#9B9B9B` — вторичный/подписи,
  фон `#F5F5F5`, рамки `#E8E8E8`, ошибки `#E02424`;
* заголовки ключевых поверхностей — **UPPERCASE с трекингом**
  (шапки таблиц 11px/700, вкладки, секции, eyebrow-подписи KPI);
* шапки таблиц — светлые с зелёной линией-акцентом (и в UI, и в Excel),
  числа — tabular-nums; радиусы: кнопки 4, карточки 8;
* шрифт Inter с офлайн-фолбэком на системные (Google Fonts не подгружаем —
  приложение работает без интернета; если Inter установлен на машине,
  используется он).

Все токены — в одном модуле **`src/core/brand.py`** (используется и UI
через CSS-переменные, и Excel-экспортом): правка одного файла перекрашивает
всё приложение и отчёты.
